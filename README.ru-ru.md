# LeetCode на OCaml

![CI](https://github.com/AF2B/Leetcode/actions/workflows/ci.yml/badge.svg)
![License: MIT](https://img.shields.io/badge/License-MIT-yellow.svg)
![OCaml](https://img.shields.io/badge/OCaml-5-orange.svg)

Коллекция решений задач LeetCode, полностью написанных на OCaml. Каждая
решённая задача сопровождается автоматическим модульным тестом, а одна и та
же задача часто решается более чем одним способом — грубой силой,
оптимизированно, рекурсивно и так далее — все варианты сосуществуют в одних
и тех же файлах, с автоматическими проверками сборки, тестов и
форматирования при каждом pull request.

## Зачем несколько подходов к одной задаче

Решить задачу один раз — доказательство того, что вы нашли ответ. Решить её
ещё раз через грубую силу, ещё раз в оптимизированном варианте, ещё раз
рекурсивно (или любым другим возможным способом) — доказательство того, что
вы понимаете, *почему* ответ работает, и оставляет ориентир для того, как
одна и та же идея выглядит при разных ограничениях. Это не обязательное
требование для каждой задачи, но структура готова к этому всегда, когда это
того стоит.

## Структура репозитория

```
solutions/
  0001-0100/
    0001-two-sum/
      README.md         # описание условия, ссылка, сложность, теги
      dune               # определение тестового исполняемого файла
      solution.mli       # публичный интерфейс
      solution.ml        # реализация
      test.ml            # тесты Alcotest
  0101-0200/
    ...
```

Задачи группируются диапазонами по 100, чтобы репозиторий оставался удобным
для просмотра и после задачи #3000. Каждая задача — это одна папка ровно с
четырьмя файлами — никогда не папка на каждый подход: если задача решена
несколькими способами, каждый подход — это отдельная функция в одних и тех
же `solution.mli`/`solution.ml`, покрытая своим случаем в одном и том же
`test.ml`. `README.md` задачи описывает саму задачу (краткое условие,
ссылку, сложность, теги), а не подходы — они документируются комментариями
OCamldoc в `solution.mli`.

Каждая задача обязана иметь тест — решение без `test.ml`, покрывающего его,
не считается завершённым.

Задачи по SQL не имеют осмысленного эквивалента на OCaml (LeetCode ожидает
SQL-запрос, а не программу), поэтому устаревшая папка `sql/` остаётся как
есть и не входит в область этой миграции.

## Соглашение о коммитах

Каждый коммит помечается эмодзи, описывающим его назначение:

| Эмодзи | Значение |
|---|---|
| 🟢 | Решение **лёгкой** задачи |
| 🟡 | Решение задачи **средней** сложности |
| 🔴 | Решение **сложной** задачи |
| 🐛 | Исправление бага |
| 📝 | Обновление документации |
| 🚀 | Улучшение производительности |
| ⚡️ | Рефакторинг |
| 🎨 | Форматирование / структурные изменения |
| 🚧 | Работа в процессе |
| 🔧 | Инструменты, сборка или изменения CI |

## Сборка и запуск тестов локально

Требования: OCaml ≥ 5.0, [dune](https://dune.build) ≥ 3.0 и
[Alcotest](https://github.com/mirage/alcotest).

```bash
opam install . --deps-only --with-test
dune build @all
dune runtest
```

## Непрерывная интеграция

Каждый pull request проходит две проверки:

1. **Сборка и тесты** — `dune build @all` и `dune runtest` для `test.ml`
   каждой задачи, с набором предупреждений dev-профиля, трактуемым как
   ошибка (заменяет отдельный линтер).
2. **Проверка форматирования** — `dune build @fmt`.
